## 原则一：Evidence Driven（证据驱动）

任何协议修改，必须先回答两个问题：

```text
为什么改？
证据是什么？
```

反例（不构成升级理由）：
- "我觉得这样更合理"
- "以前一直这样，感觉该调整了"

正例（构成升级理由）：
```
为什么改？
发现 Default Ranking ≠ Upvote Ranking。

证据是什么？
知乎真实页面对比。
```

没有证据，协议不升级。前 10 篇 Production 期间，即使发现协议本身有问题，也先记录证据，不立即改协议，统一在 ZH-MILESTONE-010 复盘时处理（除非同一类问题在第 7 篇前重复暴露，触发生产审计决策流程 V1.0 里已经写好的例外条款）。

## 原则二：Decision 冻结的是认知目标，不是固定句式

**Semantic Target ≠ Literal Target。**

Decision 中的核心判断（Core Judgment）等字段规定的是**认知目标**——读者读完后必须获得的判断，而不是必须逐字出现的句子。Execution IR 把它编译为本篇特有的 Acceptance Criteria；AUDIT 验证标准是**语义一致**，不是**字面一致**。

例：Decision 规定核心判断"这不是任务回来了，是风险换了个包装回来了"。只要正文能让读者明确得到"别人交给你的不是机会，而是风险"这个认知，无论具体怎么措辞（"风险只是换了一层包装""真正交到你手里的不是机会""接回来的往往不是项目，而是历史问题"……），都算兑现 Acceptance Criteria，不需要逐字还原。

**为什么加这条**：机械要求逐字复现会让 Execution IR 退化为模板填空，抹杀 WRITE 在具体表达上的空间，长期会让所有产出的首屏句式趋同，反而制造新的规整化风险。

**如何应用**：AUDIT 阶段发现"正文与 Execution IR 措辞不同"，不能直接判定为不一致；必须先判断认知/判断本身是否传达到位，再决定是否构成 Issue。（首次应用见 ZH-20260801-003 Decision_Log.md Issue-01，原始记录以 Production Card 措辞留存，见历史）

## 原则三：零 Issue 也是合法结果

**AUDIT ↓ Issue = 0 ↓ 直接 REVIEW**，不强制每篇都必须走 AUDIT → Issue → Patch。

Draft 干净、无可归入七类证据标准的问题，不代表 AUDIT 没做，代表 WRITE 阶段这次一次通过。**不要求 Claude 为了证明审计"有价值"而制造一个 Issue**——这是很多编辑流程会退化出的通病，审计者为了自证存在感，倾向于"改一点"。

**为什么加这条**：ZH-20260801-004 是首个 Clean Pass 样本（AUDIT 未发现 Issue，Draft-v1.md 本身可作为用户验收稿，无需生成 Article-Patched 版本）。这证明 WRITE 阶段本身可以一次通过，不是所有文章都必须经过 Patch。

**理想分布（假设，待 10 篇验证）**：约 70% Draft 直接进入用户验收，约 30% Draft 经 Patch 后进入用户验收。如果比例走向 100% 都需要 Patch，说明 WRITE 阶段在退化，应回头检查 Execution IR 是否自给自足（Acceptance Criteria 是否完整）、Claude正文生产Prompt 是否越权（是否在 WRITE 步骤重新推导了 Decision/Execution IR）、WRITE 是否未执行 Execution IR 义务，而不是继续加强 AUDIT/Patch 环节。

**统计口径**：Production Ledger 新增 Audit Result 列（Issue / Clean Pass），供 ZH-MILESTONE-010 统计 Clean Pass 率、平均 Issue 数、Patch 率、Patch Validation 通过率和用户验收结果。

## 原则四：做信息隔离，不做对象膨胀

系统新增能力时，优先修改已有对象的规则，不新增平行对象。

默认修改字段，禁止新增对象。只有当现有对象无法表达，且连续多个案例证明字段无法承载时，才允许新增对象。

新增对象前必须先回答：

```text
能不能放进已有对象？
能不能通过新增字段表达？
能不能通过修改触发条件、禁用边界、状态或权重解决？
```

当前固定两个核心对象，各自拥有独立的生命周期状态，不共用状态名，不发生对象类型变异（一个对象的记录不会在生命周期中变成另一个对象的记录）：

| 对象 | 权威文件 | 职责 | 生命周期 |
|---|---|---|---|
| Observation（观察） | `data/Milestone_Observations.md` | 记录和验证：观察到了什么、来自哪些样本、如何验证、证据是否支持 | `OPEN → VALIDATING → SUPPORTED / REJECTED / INCONCLUSIVE → CLOSED` |
| Parameter（参数记录） | `production_variable_library.md` | 生产调度：参数是什么、当前是否具备触发资格、由哪些 Observation 支撑、何时进入或退出生产 | `DISCOVERED → CANDIDATE → REVIEW → ACTIVE → DEPRECATED → ARCHIVED` |

两者的连接方式是引用，不是状态映射：Parameter 记录用"证据引用（Evidence References）"字段保存支撑它的 Observation ID 列表；Observation 用"关联 Parameter ID"字段指向（如已存在）对应的参数记录。一条 Observation 达到 `SUPPORTED`，不会自动创建或推进 Parameter 记录——是否创建/推进，仍需人工或治理评审判断。

Evidence（证据）不单独成为第三个对象：证据正文始终保存在 Observation 里，Parameter 只保存引用，不复制证据正文。Governance（治理）也不单独成为对象：由本文件（系统治理原则）定义规则，不建立独立记录系统。

只有 `ACTIVE` 状态的 Parameter，才允许被 COMPILE 触发（Trigger）并写入本次 Execution IR；`DISCOVERED`、`CANDIDATE`、`REVIEW` 状态的参数只允许在指定单变量实验中触发，`DEPRECATED`、`ARCHIVED` 禁止触发。`CANDIDATE` 允许长期停留，不强制在固定时间内推进或废弃——发现新规律但证据不足时，记录为 Candidate，不必立刻决定"加入正式库"或"彻底放弃"。

执行边界：

1. 审核发现问题，只写 Observation（状态 OPEN）。
2. 未完成平台验证，不改正式参数。
3. Observation 结论为 REJECTED 或 INCONCLUSIVE，Observation 关闭（CLOSED），不创建或推进 Parameter 记录。
4. Observation 结论为 SUPPORTED，才可能修改对应 Parameter 记录的字段，或创建新的 Parameter 记录（初始状态为 DISCOVERED 或 CANDIDATE，视证据强度而定）。
5. 每次参数修改必须在 Parameter 记录中关联 Observation ID。
6. 不新增独立 Trigger、Evidence、Change Log 系统。

最终闭环：

```text
生产
↓
审核
↓
Observation
↓
平台验证
↓
参数修改判断
↓
更新参数库
↓
记录变更
```

## 原则五：状态报告只报事实

Codex 在生产、审核、发布链路中的收口输出必须像流水线状态报告，只报告事实，不做项目复盘、不做价值评价、不扩展建议。

禁止输出：

- 今天最大的成果
- 这比单纯完成一篇文案更有价值
- 第一次完成某某闭环
- 建议新增审核原则
- 与当前节点无关的阶段复盘

统一输出格式：

```text
当前状态：
READY_FOR_XXX

已完成：
✓ ...

未完成：
□ ...

阻塞项：
...

下一步：
...

下一步责任人：
...
```

状态命名必须区分“已完成”和“等待执行”。例如：

- `READY_FOR_BODY_GENERATION` 表示等待正文生产，不表示正文已生成。
- `BODY_GENERATED` 表示正文已生成。
- `READY_FOR_AUDIT` 表示等待审核。
- `READY_FOR_LINK_REPLACEMENT` 表示等待真实链接替换。
- `READY_FOR_RELEASE` 表示发布前所有阻塞项已清空。

## 原则六：单一事实来源

任何内容知识只能存在于一个权威位置。系统允许多个对象协作，但不允许多个对象同时维护同一类内容规则。Production Card 已随九对象链退役；本原则的对象模型对齐 `docs/知乎OS Compiler V1.md` 七节点。

| 内容 | 唯一权威 |
|---|---|
| Reality / Main Gap / Transformation / Core Judgment | Decision（DECISION 节点输出） |
| 正文结构、素材边界、本篇特有验收标准、Reasoning Path | Execution IR（COMPILE 节点输出） |
| 正文模型执行边界（人话表达、节奏、留白） | Runtime.Writer Rules（`templates/Claude正文生产Prompt.md`） |
| 生产状态、角色交接、发布顺序 | `docs/生产状态机与交接规范.md` |
| 通用可判定表达检查规则 | Runtime.Audit Rules（`templates/GPT审核清单.md`） |
| 参数定义、变量状态、验证证据 | 参数库 / 变量库 |
| 最终发布决定 | 用户验收（REVIEW） |

治理规则：

1. Decision + Execution IR 是正文阶段唯一内容权威，两者合称 SSP 表所指的"内容知识"。
2. Claude正文生产Prompt 只允许承载 WRITE 的执行边界，不得承载内容知识、历史参数、推理模型或正文结构本身。
3. AUDIT 只检查正文是否符合 Execution IR 的 Acceptance Criteria 与 Runtime.Audit Rules，不得引用两者之外的历史参数体系作为内容标准。
4. RELEASE 只记录 Runtime Version、AuditResult、Approval 和 Release Decision，不得重新引入旧参数版本或旧协议版本作为发布依据。
5. 如果同一条内容知识同时出现在两个对象中，视为需要治理；优先保留权威对象，删除或降级非权威对象。

目标链路：

```text
INPUT
↓
DECISION
↓
COMPILE（产出 Execution IR）
↓
WRITE（只执行，不解释内容）
↓
AUDIT（只审 Execution IR + Runtime.Audit Rules 一致性）
↓
REVIEW（用户阅读最终正文，唯一验收权）
↓
RELEASE
```

## 原则七：Evidence Traceability（证据可追溯）

任何进入 `production_variable_library.md` 的 ACTIVE 参数，都必须能向下追溯到至少一个 L1 代表样本；任何 L1 代表样本，都必须能向下追溯回 L0 内容资产总账。

正向链路：

```text
L0 内容资产
↓
L1 代表样本（说明为什么进入 L1）
↓
Blind Review（先自然比较，不先套参数库）
↓
Candidate（候选规律）
↓
未来新文章验证
↓
ACTIVE Parameter
```

反向链路：

```text
ACTIVE Parameter
↓
Evidence References / Candidate 记录
↓
L1 样本
↓
L0 article_id
```

治理规则：

1. L0 回答“事实和历史位置”：这篇内容是什么、结果怎样、处在账号历史哪个分位。
2. L1 回答“为什么值得深挖”：Top Performer / Bottom Performer / Outlier / Recent Production 入口可以并存，一篇文章可以同时命中多个入口。
3. Blind Review 回答“自然读者为什么看、收藏或退出”：第一轮不得先套 ACTIVE、PD、BT 等既有参数标签。
4. Candidate 回答“这个差异是否值得未来验证”：历史样本只能形成 CANDIDATE，不得直接升级 ACTIVE。
5. ACTIVE 回答“是否允许进入日常生产触发”：必须有未来新文章验证和账号基准对照。
6. 任何无法追溯到 L1 / L0 的 ACTIVE 参数，视为证据引用缺口，必须补录证据或降级评估。

## 原则八：Production Boundary（生产边界）

模块只能输出自己职责范围内的对象，不得提前生成下游模块拥有最终决策权的对象。

这是职责边界，不是 Prompt 技巧。上游模块可以提供事实、候选、排序、证据和可选空白，但不能替下游模块完成最终生产决策。

固定边界：

| 模块 / 对象 | 允许输出 | 禁止输出 |
|---|---|---|
| Trigger Candidate | 生产优先级、题目模式排序、值得尝试的 Question Pattern | ACTIVE、正文结构、参数、核心判断、正文方向 |
| Topic Package | 题目事实、原问题、必要上下文、是否值得写、重复检查、风险提示、`Answer_Benchmark_Top3`、已有观点覆盖、可能空白、现有参数命中、待审核参数缺口 | ACTIVE、核心判断、正文结构、最终参数、表达策略 |
| 读者视角校准（选题包「3. 读者视角校准」节） | 读者真实困惑、读者原始理解、实际读者范围——三字段唯一权威来源 | ACTIVE、核心判断、正文结构、参数、正文方向、Gap |
| Answer_Benchmark_Top3 | 同题高赞回答前三的竞争环境、已覆盖内容、`Possible_Current_Gap`、现有参数命中证据、待审核参数缺口 | Current Direction、唯一核心判断、正文主线、ACTIVE、参数新增或状态推进 |
| Current Gap | 候选空白、可考虑差异点 | 正文方向、必须采用的论证路径 |
| Blind Review | 阅读体验差异、候选观察、样本事实 | ACTIVE 参数、Prompt 修改、生产协议修改 |
| Candidate | 候选规律、适用范围、证据来源、验证方向 | ACTIVE 规则、默认触发参数、正文模板 |
| DECISION / COMPILE（正文生产决策层） | 真正采用哪个 Gap、唯一核心判断、ACTIVE、参数、结构、表达 | 不适用 |

读者真实困惑、读者原始理解、实际读者范围三个字段，属于 Single Source of Truth：只能由选题包「3. 读者视角校准」节生成一次，跨过 INPUT Boundary 进入 Input Package。DECISION 必须直接消费这三个字段，不得重新推导、改写或生成第二份版本；即便 DECISION 认为选题包中的字段有误，也必须退回选题包修正，不允许在 Decision 内部另建一份同名但不同内容的字段（避免出现 A/B 两个事实来源随时间漂移）。

`Current Gap` 必须理解为 `Possible Current Gap`。`Answer_Benchmark_Top3` 可以指出"别人已经写了什么、还有哪些空白"，但 DECISION 可以不用这些 Gap，也可以重新推导出新的 Gap。Candidate Gap 仅为研究结论，不属于 DECISION 输入，不具有约束力；Claude 在 DECISION 步骤可以接受、修改、否决，或完全重新定义正文切入。`Answer_Benchmark_Top3` 不得变成第二个 Decision 权威。

`ACTIVE`、核心判断、最终参数、结构和表达，必须在 Claude 执行 DECISION / COMPILE 的过程中，结合题目、`Answer_Benchmark_Top3`、`Possible_Current_Gap`、Historical Baseline、Trigger Candidate 和知识库共同推理得出。它们不是 Topic Package、`Answer_Benchmark_Top3` 或 Trigger Candidate 的输入结论。

违反示例：

- 题目命中 `公司为什么...`，所以直接指定 `ACTIVE-03`。
- `Answer_Benchmark_Top3` 写出“本文应该写 X”。
- Current Gap 直接变成正文方向。
- Blind Review 直接形成 ACTIVE 参数。
- Candidate 直接进入默认生产触发。

合规示例：

- Trigger Candidate 输出“本题优先级高，原因是命中公司为什么类 Trigger”。
- `Answer_Benchmark_Top3` 输出“同题高赞回答已覆盖 A/B/C，可能空白为 D/E/F”。
- DECISION 再决定是否采用 D/E/F，或改用 G，并说明理由。

## 原则九：Increment over Replacement（增量优先，禁止默认覆盖）

任何新增能力，默认建立在已验证能力之上；未经明确否定，不得覆盖已验证内容。

```text
Verified
↓
Freeze
↓
Continue
↓
Verified
↓
Freeze
↓
Continue
```

不是：

```text
Verified
↓
Rewrite
```

**为什么加这条**：正文生产、Patch 和系统演化反复出现同一模式——新的分析或能力一出现就整体覆盖已验证内容，结果是单篇内局部变好但整体阅读体验下降，系统整体变丰富但生产效率下降，每次修一个问题就丢掉原来已经成立的优点。这不是单篇正文问题，是执行方式的系统性错误。

**如何应用**：

- 正文生产：不是重新写全文，而是"上一层成立 → 保留 → 继续向下推导下一层"，例如现实 → 原因 → 根因 → 出路 → 更高层结论，每层成立后冻结，只继续向后延伸，不重写已成立的层。
- Patch：默认动作是 Assets 保持不变 + Issues 局部修改；禁止把 Issues 当作全文重写的理由。
- QA：判定 Issue 时必须同时说明哪些内容已验证有效、需要保留，不能只输出问题列表。
- Compiler / Prompt / 系统设计：任何 Proposal 默认是 Old + New（在已验证内容基础上扩展），禁止默认 Old → Replace；除非能明确证明旧能力本身错误，否则新增能力只能扩展，不得覆盖。

本条是执行原则（Implementation Principle），不新增 Layer、不新增 Object、不新增 Compiler、不新增 Protocol，不修改《内容架构总则》。

## 系统当前的三层结构

| 层级 | 内容 | 状态 |
|---|---|---|
| 生产层 | 知乎问题 → Daily_Topic_Top3 → Answer_Benchmark_Top3 → Topic Package → INPUT → DECISION → COMPILE（Execution IR）→ WRITE（Draft）→ AUDIT → Patch / Patch Validation（仅有 Issue 时）→ REVIEW → RELEASE | 已稳定，可连续生产 |
| 研究层 | Answer_Benchmark_Top3 样本来源拆分为 Default / Upvote / Latest（不再混用"高赞=平台样本"） | 本轮新稳定 |
| 参数层 | Observation → 平台验证 → 参数修改判断 → 参数库回写 | 只改已有权威对象，不新增平行系统 |

1. **参数治理**：哪些 Candidate 参数连续出现，哪些只是偶然
2. **流程复盘**：Audit 提出的问题里，重复率最高的是哪几类，是否说明 Production 阶段存在固定短板
3. **Answer_Benchmark_Top3 采样效果分析**：Default Answer_Benchmark_Top3 训练出的文章，是否比 Upvote Answer_Benchmark_Top3 更接近知乎真实分布
4. **生产质量趋势分析**：Execution IR 是变短了还是变复杂了

**在 ZH-MILESTONE-010 之前，禁止改协议**，只允许按 Evidence Driven 原则记录证据。

## 参数发现链路冻结

从 V1.12 起，参数发现链路进入运行验证阶段，不再继续扩展字段或新增对象。

冻结对象与编号：

| 对象 | 编号格式 | 说明 |
|---|---|---|
| 参数缺口 | `Gap-001` | AI 或审核发现现有参数解释不了的现象 |
| 候选参数 | `Candidate-001` | 用户审核后同意进入观察 / 验证的候选 |
| 正式参数 | `PD-09` / `RR-02` / `CR-01` | 参数库正式参数，只有 ACTIVE 可日常触发 |

参数缺口必须记录 `Source`，固定来源为：高赞Top3 / 用户发布结果 / 人工审核 / 老师样本 / 历史数据库 / 评论区 / 数据复盘。

下一阶段只做真实生产验证，核心观察指标：

1. 30 篇内发现多少个 `Gap`。
2. 多少个 `Gap` 被驳回、合并、进入 `Candidate`。
3. 最终多少个 `Candidate` 经过验证成为 `ACTIVE`。

治理成功的表现是：大量 Gap 被筛掉，少量进入 Candidate，极少数成为 ACTIVE。若 Gap 大量直接成为 ACTIVE，视为治理失败。

参数验证因果边界：

```text
高赞回答
↓
参数命中统计
↓
高频参数 / 参数缺口
↓
COMPILE 触发
↓
本账号发布
↓
阅读 / 赞同 / 收藏 / 评论 / 收益
↓
效果验证
↓
ACTIVE
```

禁止使用以下推理：

```text
高赞回答命中某参数
↓
说明该参数导致高赞
↓
直接验证参数有效
```

`Answer_Benchmark_Top3` 只能证明某参数出现在高赞回答中，不能证明该参数造成高赞。真正的参数验证永远来自本账号发布结果。

## 选题过滤规则：开放式决策题

开放式决策题默认不进入正式生产。

本规则只属于 Topic Pool 筛选规则，不属于参数库更新、生产流程更新或正文规范更新。

判定标准：

1. 问题主体是“如果你……”“你会不会……”“你会怎么选……”“你会如何处理……”。
2. 核心目标是让回答者做选择。
3. 答案无法抽象出稳定机制，只能输出个人选择、价值观、风险偏好或管理风格。

稳定判断法：

```text
如果把题目改成“为什么”，仍然能够回答机制，则保留。
如果改成“为什么”以后问题就不存在了，直接放弃。
```

处理结果：

- 问题类型：开放式决策题
- 状态：REJECT
- 不进入 INPUT
- 不采集 `Answer_Benchmark_Top3`
- 返回 Topic Pool 继续选题
