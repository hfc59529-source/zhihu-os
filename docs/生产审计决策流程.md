# 生产审计决策流程 V1.0

版本：AUDIT-DECISION-FLOW-V1.0

状态：FROZEN（三方——用户、Claude、GPT——确认冻结，连续执行 10 篇 Production 期间不新增节点、不改职责、不改协议；若第 7 篇前重复暴露同一类问题，视为流程问题再升级，否则记录留待 10 篇结束统一复盘）

## 核心原则

生产（Production）、审计（Audit）、决策（Decision）、执行（Patch）四个职责分离，避免同一方既发现问题又给答案又自己拍板。

## 职责表（三方确认版）

| 阶段 | 负责人 | 输出 |
|---|---|---|
| Production | Codex | Draft-v1（冻结） |
| Audit | Claude | Audit_Report |
| Decision | GPT | Approve / Reject / Revise |
| Patch | Claude（依据 Decision） | Patch.diff |
| Validation | GPT | Final Validation |
| Release | Codex | Release-v1 |

## 铁律：审计必须基于可验证证据，不得基于个人写作偏好提出修改建议

Audit_Report 中的 Problem / Risk 只能基于以下可验证类别：

- 重复（同一语义在短距离内复现）
- 跳跃（逻辑链缺失中间环节）
- 逻辑断裂（因果不成立）
- 证据不足（关键判断无支撑）
- 与 Production Card 不一致
- 阅读障碍（语法/指代/结构导致理解成本过高）
- 事实风险（涉及未经核实的承诺、数据、政策）

**禁止**出现"感觉更顺""我更喜欢""读起来舒服""建议更有力量"这类风格偏好表述。否则 Claude 和 GPT 会各自倾向不同文风，系统判断标准会逐渐漂移，失去可复现性。

## 完整闭环

```text
Codex
│
├── Draft-v1（冻结）
│
▼
Claude
│
├── Audit_Report（标准格式，只提问题，不写 Patch）
│
▼
GPT
│
├── Approve
├── Reject
└── Revise
│
▼
Claude
│
└── Patch.diff（GPT Approve/Revise 之后才写，不能提前写）
│
▼
Apply Patch（Codex 执行）
│
▼
Final Validation（对照 Production Card 的机械校验，不重新全文审核）
│
▼
Release（用户确认发布）
│
▼
Production Ledger（记录 + Decision_Log 归档）
```

## 关键规则

1. **Claude 不提前写 Patch**。Audit_Report 提交后必须等 GPT 输出 Approve / Reject / Revise，Claude 才能动笔写 Patch.diff。提前写好的 Patch 等于把结论塞给 GPT，破坏独立判断。
2. **Draft 冻结**。Draft-v1.md 一旦生成不可被 Claude 直接修改，任何改动只能以 Patch 形式提出并经过审核链路。
3. **Final Validation 不是重新全文审核**，只检查四项（GPT 固定清单）：
   - [ ] 是否符合 Production Card
   - [ ] 是否解决 Issue
   - [ ] 是否引入新 Bug
   - [ ] 是否存在误删
   全部 PASS 才能进入 Release。类似 CI，不是二次总审。
4. **每篇 Production 必须有 Decision_Log.md**，记录每个 Issue 的 Claude 判断、GPT 判断、最终决定、负责人、原因。这比 Patch 本身更重要，是未来回溯"为什么这么改"的唯一依据。

## Audit_Report 标准格式

每个问题独立编号：

```text
Issue-01

位置：
（行号或段落定位）

严重等级：
Critical / Major / Minor

Evidence：
（原文引用）

Problem：
（发现的问题是什么）

Risk：
（如果不处理，可能的后果）

Suggestion：
（Claude 的倾向性意见，仅供参考，不是结论）

Need GPT Review：
YES
```

GPT 审核时只需对每个 Issue 输出：

```text
Issue-01：Approve / Reject / Revise
Issue-02：Approve / Reject / Revise
...
```

## Decision_Log 标准格式

```text
Issue-01

Claude：
（Claude 的判断和理由）

GPT：
（GPT 的判断和理由）

最终：
保留 / 修改为 ___

负责人：
（用户姓名或"系统默认"）

原因：
（为什么最终这么定）
```
