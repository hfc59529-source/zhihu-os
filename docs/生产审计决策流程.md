# 生产审计决策流程 V1.1

版本：AUDIT-DECISION-FLOW-V1.1

状态：ACTIVE

## 核心原则

生产卡生成、正文生成、QA、审计、决策、修复、终检、用户验收和发布必须职责分离，避免同一方既发现问题又给答案又自己拍板。

Codex 不写正文。Codex 可以写 Production Card、QA、审核记录、决策记录、状态记录和发布记录，但不得直接改写 `Draft-v1.md`、`Article-v*.md`、`Article-Patched-v*.md`、`Article-Final.md` 或 `Release-v*.md` 的正文段落。

## 职责表

| 阶段 | 负责人 | 输出 |
|---|---|---|
| Production Card | Codex | Card-v1 |
| Draft Production | Claude | Draft-v1 |
| QA | Codex | Codex_QA |
| Audit | GPT / 人工 | Audit_Report |
| Decision | GPT | Approve / Reject / Revise |
| Patch | Claude（依据 Decision） | Article-Patched-v1 / Patch.diff |
| Apply Patch / Archive | Codex | 变更归档、状态记录 |
| Validation | GPT | Final Validation |
| User Review | 用户 | USER_APPROVED / USER_REJECTED |
| Release | Codex | Release-v1 |
| Publish | 用户 / Codex记录 | 发布链接、发布时间 |

## 受保护正文文件

以下文件只能由 Claude / 写作角色产出或修正：

- `Draft-v1.md`
- `Article-v*.md`
- `Article-Patched-v*.md`
- `Article-Final.md`

`Release-v*.md` 是发布稿容器，不是修正文档。Codex 只有在用户验收通过后，才允许从已验收正文同步生成 `Release-v*.md`；不得在 Audit / Patch / Final Validation 阶段手写或润色其中的正文段落。

## Codex 编辑前检查

Codex 每次准备编辑文件前，必须先做三项判断：

1. 目标文件是否属于受保护正文文件。
2. 当前状态是否允许 Codex 写该文件。
3. 本次动作是否包含新增、删除、替换、润色正文句子。

只要任一项触发正文写作风险，Codex 必须停止正文编辑，改为更新 `Audit_Report.md`、`Decision_Log.md` 或状态文件，并交接给 Claude / 写作角色。

## 铁律：审计必须基于可验证证据，不得基于个人写作偏好提出修改建议

Audit_Report 中的 Problem / Risk 只能基于以下可验证类别：

- 重复（同一语义在短距离内复现）
- 跳跃（逻辑链缺失中间环节）
- 逻辑断裂（因果不成立）
- 证据不足（关键判断无支撑）
- 与 Production Card 不一致
- 阅读障碍（语法/指代/结构导致理解成本过高）
- 事实风险（涉及未经核实的承诺、数据、政策）

**禁止**出现"感觉更顺""我更喜欢""读起来舒服""建议更有力量"这类风格偏好表述。否则 Claude 和 GPT 会各自倾向不同文风，系统判断标准会逐渐漂移，失去可复现性。

## 完整闭环

```text
Codex
│
├── Production Card（冻结内容权威）
│
▼
Claude
│
├── Draft-v1（冻结）
│
▼
Codex
│
├── QA（只审 Card 一致性，不修改正文）
│
▼
GPT / 人工
│
├── Audit_Report（只提问题，不写 Patch）
│
▼
GPT
│
├── Approve
├── Reject
└── Revise
│
▼
Claude
│
└── Article-Patched-v1 / Patch.diff（GPT Approve/Revise 之后才写，不能提前写）
│
▼
Apply Patch / Archive（Codex 执行）
│
▼
Final Validation（对照 Production Card 的机械校验，不重新全文审核）
│
▼
User Review（用户阅读最终正文并确认是否可发布）
│
▼
Release（用户验收后生成 / 确认发布稿）
│
▼
Production Ledger（记录 + Decision_Log 归档）
```

## 关键规则

1. **Claude 不提前写 Patch**。Audit_Report 提交后必须等 GPT 输出 Approve / Reject / Revise，Claude 才能动笔写 Patch.diff 或 Article-Patched-v1。提前写好的 Patch 等于把结论塞给 GPT，破坏独立判断。
2. **Codex 不写 Patch 正文**。Codex 发现问题时只能定义 Issue、证据、风险、修正目标和下一状态，不能直接替 Claude 改正文。任何由 Codex 直接改写正文并推进复检的行为都视为流程事故。
3. **Draft 冻结**。Draft-v1.md 一旦生成不可被直接覆盖，任何改动只能以 Patch 或 Article-Patched 形式归档，并经过审核链路。
4. **Final Validation 不是重新全文审核**，只检查四项（GPT 固定清单）：
   - [ ] 是否符合 Production Card
   - [ ] 是否解决 Issue
   - [ ] 是否引入新 Bug
   - [ ] 是否存在误删
   全部 PASS 只能进入 USER_REVIEW。类似 CI，不是二次总审。
5. **每篇 Production 必须有 Decision_Log.md**，记录每个 Issue 的 Claude 判断、GPT 判断、最终决定、负责人、原因。这比 Patch 本身更重要，是未来回溯"为什么这么改"的唯一依据。
6. **RELEASE_READY 必须在用户验收之后**。Final Validation PASS 只表示文件和校验条件满足，不表示用户已经看过正文，也不表示可以直接发布。

## Audit_Report 标准格式

每个问题独立编号：

```text
Issue-01

位置：
（行号或段落定位）

严重等级：
Critical / Major / Minor

Evidence：
（原文引用）

Problem：
（发现的问题是什么）

Risk：
（如果不处理，可能的后果）

Suggestion：
（Claude 的倾向性意见，仅供参考，不是结论）

Need GPT Review：
YES
```

GPT 审核时只需对每个 Issue 输出：

```text
Issue-01：Approve / Reject / Revise
Issue-02：Approve / Reject / Revise
...
```

## Decision_Log 标准格式

```text
Issue-01

Claude：
（Claude 的判断和理由）

GPT：
（GPT 的判断和理由）

最终：
保留 / 修改为 ___

负责人：
（用户姓名或"系统默认"）

原因：
（为什么最终这么定）
```
