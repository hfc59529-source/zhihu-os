# 生产审计决策流程 V1.3

版本：AUDIT-DECISION-FLOW-V1.3

状态：ACTIVE

## 核心原则

选题采集、生产卡生成、正文生成、QA、审计、决策、修复、修改后确认、用户验收和发布必须职责分离，避免同一方既发现问题又给答案又自己拍板。

Codex 只负责选题采集与入库。Codex 不写 Production Card，不写正文，不做 QA，不写审核记录、决策记录、发布记录，也不得直接改写 `Draft-v1.md`、`Article-v*.md`、`Article-Patched-v*.md`、`Article-Final.md` 或 `Release-v*.md` 的正文段落。

## 职责表

| 阶段 | 负责人 | 输出 |
|---|---|---|
| Topic Package | Codex | data/topic_candidates/YYYY-MM-DD/TOPIC-YYYYMMDD-NNN.md |
| Draft Production | Claude | Draft-v1 |
| Audit | GPT / 人工 | 参数审核清单、正文审核清单、PASS / 正文问题 / 系统问题 |
| Decision（仅 Audit 有 Issue 时） | GPT | Approve / Reject / Revise |
| Patch | Claude（依据 Decision） | Article-Patched-v1 / Patch.diff |
| Apply Patch / Archive | Claude / 后续生产角色 | 变更归档、状态记录 |
| 修改后确认（仅发生 Patch 后） | GPT / 人工 | 修改有效确认 |
| User Review | 用户 | User_Review_Package / USER_APPROVED / USER_REJECTED |
| Release | Claude / 用户 | Release-v1 |
| Publish | 用户 / 后续生产角色记录 | 发布链接、发布时间 |

## 受保护正文文件

以下文件只能由 Claude / 写作角色产出或修正：

- `Draft-v1.md`
- `Article-v*.md`
- `Article-Patched-v*.md`
- `Article-Final.md`

`Release-v*.md` 是发布稿容器，不是修正文档。Codex 不负责生成或确认 `Release-v*.md`；不得在 Audit / Patch / Patch Validation 阶段手写或润色其中的正文段落。

## Codex 编辑前检查

Codex 每次准备维护参数、知识、样本或参数调用日志前，必须先做三项判断：

1. 本次动作是否属于选题采集或系统维护。
2. 是否已经由 GPT / 人工确认系统问题或日志记录需求。
3. 目标文件是否属于受保护正文文件。

只要任一项触发正文写作风险，Codex 必须停止编辑，并交接给 Claude / 写作角色或 GPT / 人工。

## 铁律：审计必须基于可验证证据，不得基于个人写作偏好提出修改建议

Audit_Report 中的 Problem / Risk 只能基于以下可验证类别：

- 重复（同一语义在短距离内复现）
- 跳跃（逻辑链缺失中间环节）
- 逻辑断裂（因果不成立）
- 证据不足（关键判断无支撑）
- 参数调用不一致
- 阅读障碍（语法/指代/结构导致理解成本过高）
- 事实风险（涉及未经核实的承诺、数据、政策）

**禁止**出现"感觉更顺""我更喜欢""读起来舒服""建议更有力量"这类风格偏好表述。否则 Claude 和 GPT 会各自倾向不同文风，系统判断标准会逐渐漂移，失去可复现性。

## 完整闭环

```text
Codex
│
├── Topic Package（选题包）
▼
Claude
│
├── Draft-v1（冻结）
│
▼
GPT / 人工
│
├── 参数调用检查
├── 正文执行检查
├── 系统问题 / 正文问题归因
│
▼
GPT / 人工
│
├── Audit PASS
│   ▼
│   User Review（用户阅读最终正文并确认是否可发布）
│
└── Audit Issue
    ▼
GPT
│
├── Approve
├── Reject
└── Revise
│
▼
Claude
│
└── Article-Patched-v1 / Patch.diff（GPT Approve/Revise 之后才写，不能提前写）
│
▼
Apply Patch / Archive（Claude 执行）
│
▼
GPT / 人工确认修改有效（只在发生 Patch 后执行）
│
▼
User Review（用户阅读最终正文并确认是否可发布）
│
├── USER_REJECTED
│   ▼
│   Decision（根据用户指出的问题裁决是否修复）
│   ▼
│   Claude Patch → GPT / 人工确认修改有效 → User Review
│
└── USER_APPROVED
    ▼
Release（用户验收后生成 / 确认发布稿）
│
▼
参数调用日志（Codex 记录调用事实和结果）
```

## 关键规则

1. **Claude 不提前写 Patch**。Audit_Report 提交后必须等 GPT 输出 Approve / Reject / Revise，Claude 才能动笔写 Patch.diff 或 Article-Patched-v1。提前写好的 Patch 等于把结论塞给 GPT，破坏独立判断。
2. **Codex 不进入正文修复链路**。正文问题由 GPT / 人工定位并交 Claude 修复；系统问题连续成立后才反馈 Codex 维护参数、Prompt 或调用规则。
3. **Draft 冻结**。Draft-v1.md 一旦生成不可被直接覆盖，任何改动只能以 Patch 或 Article-Patched 形式归档，并经过审核链路。
4. **Decision 只在 Audit 有 Issue 时执行**。Audit PASS / Issue = 0 时，不需要空跑 Decision，不需要为证明流程完整而制造裁决记录。
5. **每篇 Production 必须有参数调用日志**，记录 Claude 声称调用参数、GPT / 人工确认实际生效参数、GPT / 人工归因和发布后表现。这是未来回溯参数是否有效的依据。
   若 Audit PASS / Issue = 0，Decision_Log 可记录 `Issue = 0 / No Decision Required`，不得强制生成空裁决。
6. **修改后确认只在发生 Patch 后执行**。无问题正文在 Audit PASS 后直接进入 `READY_FOR_USER_REVIEW`；有问题正文在 Claude Patch 后，由 GPT / 人工确认修改是否有效，再进入 `READY_FOR_USER_REVIEW`。
7. **RELEASE_READY 必须在用户验收之后**。Audit PASS 或修改后确认通过只表示审核条件满足，不表示用户已经看过正文，也不表示可以直接发布。
8. **进入 Release / Publish Queue 的唯一入口是 USER_APPROVED**。只有用户明确 `USER_APPROVED` 后，后续生产角色才能生成或确认 `Release-v1.md`，并将状态更新为 `RELEASE_READY`。
9. **USER_REJECTED 返回路径**。用户拒绝后，必须根据用户指出的问题进入 Decision；若需要修复，由 Claude 修复正文，再回到 GPT / 人工确认修改有效和 `READY_FOR_USER_REVIEW`。Codex 不得借用户拒绝直接改写正文。
10. **用户验收必须有上下文包**。进入 `READY_FOR_USER_REVIEW` 时，后续生产角色必须提供 `User_Review_Package.md` 或等价展示，包含 Production ID、原知乎问题、真实问题链接、当前正文版本、当前状态和完整正文内容。正文文件可以是纯正文，但不得把无头正文直接交给用户验收。
11. **Release 不能前置替代验收包**。未获得 `USER_APPROVED` 前，不得把 `Release-v1.md` 当作用户验收包、正式发布稿或 Publish Queue 入队依据。

## Audit_Report 标准格式

每个问题独立编号：

```text
Issue-01

位置：
（行号或段落定位）

严重等级：
Critical / Major / Minor

Evidence：
（原文引用）

Problem：
（发现的问题是什么）

Risk：
（如果不处理，可能的后果）

Suggestion：
（Claude 的倾向性意见，仅供参考，不是结论）

Need GPT Review：
YES
```

GPT 审核时只需对每个 Issue 输出：

```text
Issue-01：Approve / Reject / Revise
Issue-02：Approve / Reject / Revise
...
```

## Decision_Log 标准格式

```text
Issue-01

Claude：
（Claude 的判断和理由）

GPT：
（GPT 的判断和理由）

最终：
保留 / 修改为 ___

负责人：
（用户姓名或"系统默认"）

原因：
（为什么最终这么定）
```
