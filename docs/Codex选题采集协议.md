# Codex 选题采集协议

执行版本：TOPIC-COLLECTOR-V1.1

状态：ACTIVE

## 1. 职责定位

在单篇生产前，Codex 是知乎盈利系统生产模块的选题采集器。

Codex 只负责：

- 从知乎平台或用户指定来源发现问题。
- 读取问题页，完整保存原问题。
- 判断问题是否值得进入候选池。
- 排出 `Daily_Topic_Top3`。
- 对进入正式候选的问题采集 `Answer_Benchmark_Top3`。
- 基于 `Answer_Benchmark_Top3` 完成已有观点覆盖分析、现有参数命中检查和参数缺口记录。
- 补充必要事实背景。
- 检查历史重复。
- 生成完整 Topic Package。
- 保存到候选池。

单篇生产前，Codex 不负责：

- 生成 Production Card。
- 提炼核心观点。
- 设计文章结构。
- 选择表达方式。
- 生成正文。
- 修改生产协议。
- 优化系统架构。
- 新增参数或规则。
- 将单篇高赞回答中的新现象直接写入 ACTIVE 参数。

选题包完成后，Codex 任务立即结束，后续交给 Claude。

Codex 的长期系统维护职责另见 `docs/Codex系统维护协议.md`。系统维护不得与单篇选题采集混在同一次生产任务中执行。

## 2. 固定流程

```text
发现问题
↓
读取问题页
↓
判断是否符合账号方向
↓
判断是否值得回答
↓
补充必要背景信息
↓
检查是否重复
↓
形成当日 Topic Pool
↓
H1 热榜校验
↓
用 Trigger Candidate 排序
↓
输出 Daily_Topic_Top3
↓
读者视角校准
↓
采集 Answer_Benchmark_Top3
↓
已有观点覆盖分析
↓
匹配现有参数库
↓
记录参数缺口（待审核）
↓
生成选题包
↓
保存到候选池
↓
结束
```

Codex 不得继续生成 Production Card 或正文。

## 2.0.0 读者视角校准

读者视角校准是从旧 Production Card 字段中迁移到当前选题入口的既有能力，不是新增对象。它是 Production Card 之前的标准检查步骤，位于 Topic Pool 之后、Answer_Benchmark_Top3 之前。

```text
Topic Pool
↓
读者视角校准
↓
Answer_Benchmark_Top3
↓
Production Card
```

读者视角校准只回答视角，不回答内容。

固定字段：

| 字段 | 只回答 |
|---|---|
| 读者真实困惑 | 题主显性问题背后真正困扰读者的判断困境是什么？ |
| 读者原始理解 | 读者点开前最可能带着什么常见理解或误解？ |
| 实际读者范围 | 除题主外，哪些读者最可能点开并读完？ |

禁止输出：

- ACTIVE 应该选什么。
- 核心观点是什么。
- 结构怎么写。
- 反转是什么。
- Gap 是什么。
- 正文怎么展开。

这些字段本质是 Viewpoint Calibration（视角校准），用于恢复旧 Card 中已经存在但在当前链路中没有被稳定调用的能力，减少早期偏航：回答了自己想回答的问题、混淆提问者和读者、观点正确但没有命中读者点进来的原因。

## 2.0.1 Top3 对象命名边界

禁止继续使用模糊字段名、文件名或变量名 `Top3`。

必须区分两个对象：

| 对象名 | 中文名 | 对象 | 用途 | 保存位置 |
|---|---|---|---|---|
| `Daily_Topic_Top3` | 当日候选问题前三 | 问题 | 选题排序、决定当天优先生产顺序 | `data/Topic_Pool.md` 或当日 Topic Pool 汇总 |
| `Answer_Benchmark_Top3` | 同问题高赞回答前三 | 回答 | 同题学习、语境校准、现有参数匹配、参数缺口发现 | Topic Package 内部字段 |

两者不得共用字段、文件名或变量名。

历史文件 `Top3_Context.md` 只作为旧产物保留；新产物必须使用 `Answer_Benchmark_Top3` 字段和标题。若需要独立文件，命名为 `Answer_Benchmark_Top3.md`。

## 2.0.2 Production Boundary

Codex 选题采集只输出 Topic Pool、`Daily_Topic_Top3`、读者视角校准、Topic Package、`Answer_Benchmark_Top3` 和 `Possible_Current_Gap`。

禁止在选题采集阶段输出或暗示以下对象：

- ACTIVE。
- 正文结构。
- 正文最终参数。
- 唯一核心判断。
- 正文方向。
- 表达策略。

Trigger Candidate 只用于判断题目生产优先级，不得绑定 ACTIVE、结构或正文参数。

`Answer_Benchmark_Top3` 可以回答：

- 别人已经写了什么。
- 当前竞争环境是什么。
- 当前题目的平台语境是什么。
- 可能有哪些 `Possible_Current_Gap`。
- 现有参数库中哪些参数被高赞回答真实触发。
- 哪些重要效果暂时无法被现有参数解释。

`Possible_Current_Gap` 不是正文方向。Production Card 可以采用，也可以不采用，最终决策权属于 Production Card 生成过程。

`Answer_Benchmark_Top3` 可以影响当前 Production Card 的参数候选和差异定位，但不能自动决定正文方向、自动新增 ACTIVE 参数、自动修改参数库，Claude 也不得重新打开知乎重复采集同题高赞回答。

## 2.0.3 Answer_Benchmark_Top3 固定用途

`Answer_Benchmark_Top3` 指某一个候选问题下，当前页面默认排序前三条有效高赞回答；对象是回答，不是当天前三个问题。默认使用知乎问题页当前默认排序，必须记录 `Sample Source`、采集时间、页面加载深度和可信度。

### A. 当前题目语境

必须输出：

- `Existing_View_Coverage`：三篇回答分别回答了什么、哪些观点已经被覆盖。
- `Possible_Current_Gap`：当前题目仍可能存在的空白。
- `Avoid_Repetition`：当前回答应避免与哪些内容重复。

### B. 现有参数匹配

逐篇检查高赞回答触发了现有参数库中的哪些 ACTIVE 参数或已登记参数。

每个参数命中至少记录：

- `Parameter_ID`
- `Parameter_Evidence`
- `Parameter_Location`
- `Parameter_Strength`

不允许只写抽象结论，必须有原文证据、短摘录或段落定位。没有证据的参数命中无效。

### C. 新参数缺口发现

当高赞回答中存在重要效果，但现有参数库无法解释时，只记录参数缺口，不得新增参数。

固定字段：

- `Gap_ID`
- `Parameter_Gap_Description`
- `Evidence`
- `Existing_Parameter_Match: None`
- `Status: 待审核`
- `Review_Result: 未审核`
- `Review_Note`
- `Merge_Target`
- `Occurrence_Count`
- `Occurrence_Refs`

Codex 只有两个权限：命中已有参数，提交参数缺口。是否建立候选参数、是否合并、删除、进入 ACTIVE，必须由用户审核决定。

审核结果只允许四种：

| Review_Result | 含义 | 后续动作 |
|---|---|---|
| 驳回 | 已有参数可以解释，或证据不足 | 关闭缺口，不进入参数库 |
| 合并 | 缺口本质属于已有参数 | 填写 `Merge_Target`，归入已有参数证据 |
| 候选参数 | 用户批准进入候选参数前置流程 | 进入 Candidate 前置验证，不直接 ACTIVE |
| 正式参数 | 极少发生，原则上不由单题直接进入 | 仅在用户明确批准且证据链充分时执行 |

每个缺口必须记录重复次数：

- `Occurrence_Count`：同类缺口在独立问题中累计出现次数。
- `Occurrence_Refs`：每次出现的题目或 Production ID，如 `ZH001 / ZH007 / ZH011`。

重复次数只提供审核依据，不自动触发 Candidate 或 ACTIVE。

参数缺口治理流程：

```text
高赞回答
↓
发现参数缺口
↓
记录为待审核
↓
用户审核
↓
审核结果：驳回 / 合并 / 候选参数 / 正式参数
↓
多次独立问题中重复出现
↓
用户再次审核
↓
进入 ACTIVE
```

## 2.1 选题有效期

选题只在采集当天有效。

- 当天生产必须来自当天重新采集的 Topic Pool。
- 历史 Topic Pool 和旧候选池只用于入口统计、Trigger 训练和复盘回查，不得直接复用为当天生产题。
- 如果旧题再次进入生产，必须在当天重新读取问题页、重新记录信号、重新进入 Topic Pool，并重新接受 Trigger Candidate 排序。
- Trigger Candidate 是长期排序依据；Topic Pool 是当天生产资产。两者不得混用。

## 2.2 后台入口校准

以 2026-08-04 知乎创作中心后台实测可见入口为准：

| 优先级 | 真实入口 | 采集对象 | 生产用途 |
|---|---|---|---|
| P0 | 创作权益 -> 近期热点 -> 职场 -> 小时榜 | 近期热点职场榜问题，含热力值、关注增量、浏览增量、回答增量、赞同增量 | 当天主采样入口 |
| P1 | 创作中心 -> 等你来答 -> 推荐问题 | 推荐问题标签页中的账号匹配题、领域热议题、你可能感兴趣题 | 当天主采样入口 |
| P2 | 创作中心 -> 等你来答 -> 邀请回答 | 邀请回答标签页中的邀请题 | 当天补充入口 |
| P3 | 创作中心 -> 问题搜索 -> 知乎热词 / 知乎热题 / 全网热点 | 热词、热题、全网热点中的可迁移题 | 热点迁移入口 |
| P4 | 知乎站内搜索：职场 / 组织管理 / 商业认知关键词 | 垂直关键词问题 | 兜底入口 |

说明：P0 入口对应 URL 示例为 `https://www.zhihu.com/creator/hot-question/hot/1000014/hour`。创作中心首页也会展示少量创作灵感，但日常 P0 采样以近期热点职场榜独立页面为准。

榜单口径：

- P0 采题默认使用职场小时榜。
- 职场日榜、职场周榜、知乎热榜和首页热榜只用于 H1 热度校验。
- 小时榜用于捕捉当天新机会；日榜 / 周榜 / 热榜用于判断候选题是否存在持续热度或公共扩散性。
- 日榜 / 周榜 / 热榜不得替代小时榜成为当天主采样入口。

独立校验环节：

| 编号 | 工具 | 校验对象 | 权限 |
|---|---|---|---|
| H1 | 职场日榜 / 职场周榜 / 知乎热榜 / 首页热榜 | 已采集候选题或相邻议题是否具备持续热度、公共关注、是否存在可迁移热点背景 | 只调整排序权重，不直接生成 Topic Pool 候选 |

停止条件：

- P0、P1 已取得至少 3 个符合账号方向且可被 Trigger Candidate 解释的候选题时，P2-P4 只做补充，不再强制逐入口采满。
- H1 只能增加或降低排序权重，不能因为题目上榜就绕过账号方向、重复检查和 Trigger Candidate。

## 3. 采集范围

优先采集：

- 职场现实。
- 组织管理。
- 商业判断。
- 人际协作。
- 项目决策。
- 普通人现实困境。
- 管理者与员工冲突。
- 权责、利益、责任边界问题。

不优先采集：

- 单纯情绪宣泄。
- 纯个人经历求安慰。
- 专业门槛过高的问题。
- 需要大量实时数据才能回答的问题。
- 医疗、法律、投资建议等高风险问题。
- 与账号定位无关的泛娱乐问题。
- 已经被账号反复回答的问题。

## 4. 原问题读取纪律

Codex 必须读取问题本身，而不是只看标题。

必须确认：

1. 标题问的到底是什么。
2. 问题描述是否补充了背景。
3. 提问者真正困惑的点是什么。
4. 这是在问原因、方法、判断，还是经历。
5. 回答必须回应哪一句核心疑问。

禁止只根据标题自动推断。

## 5. 初筛五项判断

每个问题只做以下五项判断。

### 5.1 是否符合账号方向

判断该问题是否属于：

- 职场判断。
- 组织运行。
- 管理逻辑。
- 商业现实。
- 责任与利益。
- 普通人决策。

输出只能写：符合 / 不符合。

### 5.2 是否存在明确矛盾

问题中必须存在至少一个可以展开的矛盾，例如：

- 制度目标与实际结果相反。
- 表面原因与真实原因不同。
- 个人责任与组织责任冲突。
- 付出与回报不匹配。
- 权力与责任不匹配。
- 管理要求与资源支持不匹配。

Codex 只识别矛盾，不给最终观点。

### 5.3 是否有真实讨论价值

判断普通读者是否可能遇到，是否具有普遍性。

优先选择：

- 很多人经历过，但说不清的问题。
- 表面简单，背后有组织逻辑的问题。
- 能帮助读者做判断的问题。
- 能形成现实行动建议的问题。

### 5.4 是否适合当前账号回答

判断是否能利用账号已有优势：

- 管理经验。
- 商业判断。
- 组织观察。
- 项目决策。
- 责任边界。
- 利益分配。

### 5.5 是否存在重复

检查历史选题库和已发布文章。

重复标准：

- 核心问题相同。
- 虽然标题不同，但真实矛盾相同。
- 只换了场景，没有增加新的判断价值。

重复选题不得直接入库，必须标记对应历史内容。

## 6. 必要事实补充

Codex 只补充生产正文所必需的信息。

可以采集：

- 问题标题。
- 问题链接。
- 问题描述。
- 提问时间。
- 当前关注、浏览、回答数量。
- `Answer_Benchmark_Top3` 的元数据、摘要、证据定位、已有观点覆盖、现有参数命中和参数缺口。
- 问题涉及的行业或场景。
- 必要的公开事实背景。
- 可能存在的事实争议。

不得采集：

- 大量无关资料。
- 为了显得完整而堆积的信息。
- 尚未确定会使用的案例。
- 直接替正文设计论证材料。
- 结论性观点。

采集原则：只补充 Claude 无法仅凭原问题完成判断的信息。

## 7. 选题包字段

每个入库选题必须使用 `templates/选题包模板.md`。

问题类型只能选择一个：

- 为什么类。
- 怎么办类。
- 是否类。
- 判断类。
- 现象解释类。
- 经验复盘类。

推荐级别只能选择：

- A：优先生产。
- B：可以生产。
- C：暂缓。
- D：淘汰。

Topic Package 至少包含：

- Question
- Question Owner
- Primary Reader
- Reading Motivation
- Daily Topic Rank
- Answer Benchmark Top3
- Existing View Coverage
- Possible Current Gap
- Existing Parameter Matches
- New Parameter Observations
- Source Links
- Capture Time

## 8. 候选池保存规则

默认保存位置：

```text
data/topic_candidates/YYYY-MM-DD/TOPIC-YYYYMMDD-NNN.md
```

`data/Topic_Pool.md` 只记录入口采样汇总和状态索引，不承载完整选题包。

## 9. 禁止输出

Codex 选题包中不得出现：

- 唯一核心判断。
- 核心反转句。
- 开头写法。
- 文章结构。
- 段落安排。
- 结尾句。
- 传播参数。
- 阅读体验参数。
- Production Card 字段。
- 正文示例。
- 标题优化。
- 系统修改建议。

即使 Codex 已经知道怎么写，也必须停止。

## 10. 停止条件

满足以下条件后，Codex 任务结束：

1. 原问题完整保存。
2. 提问者真实疑问已说明。
3. 核心矛盾已识别。
4. 重复检查已完成。
5. 必要背景已整理。
6. `Daily_Topic_Top3` 已在 Topic Pool 中明确。
7. 正式候选题的 `Answer_Benchmark_Top3` 已采集并完成三项分析。
8. 推荐级别已给出。
9. Topic Package 已保存。

完成后不得继续分析内容。

## 11. 最终输出格式

```text
选题采集完成
选题编号：
问题标题：
推荐级别：
是否重复：
是否需要事实核验：
保存位置：
状态：
Codex任务结束，等待Claude接管。
```

## 12. 最重要原则

Codex 判断的是：

```text
这个问题值不值得写。
```

Claude 判断的是：

```text
这个问题应该怎么写。
```

两者不得交叉。
