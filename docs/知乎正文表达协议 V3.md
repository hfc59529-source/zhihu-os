# 知乎正文表达协议 V3

Status：ACTIVE

## 协议定位

本协议位于 Production Card、正文推理协议与正文生产 Prompt 之间。

```text
Production Card
↓
知乎正文推理协议 V1.0
↓
知乎正文表达协议 V3
↓
Claude 正文生产 Prompt
↓
正文
```

本协议只负责“怎么说出来”。

它不决定写什么，不新增变量，不改变核心机制，不修改 Production Card，不替代 QA。

## 总原则

优秀知乎回答不是把机制讲正确，而是让读者一路读下去，并在结尾带走一个判断工具。

正文表达必须同时完成：

- 读者看得懂。
- 读者愿意继续看。
- 抽象机制能落到现实场景。
- 每段都有推进。
- 结尾不是总结，而是可复用判断。

## EP-01｜先讲现象，不先讲概念

正文开头优先从读者见过的现象、困惑或反差进入。

不要一上来定义概念、拔高问题或抛抽象判断。

错误：

```text
高层本质上是组织风险节点。
```

正确：

```text
很多人会发现一个奇怪的现象：有些能力一般的高层，老板反而一直没动。
```

然后再推出机制：

```text
原因不是能力，而是替换风险。
```

## EP-02｜每个机制必须落到具体动作

机制不能停在抽象词。

每出现一个机制，下一步必须说明组织里具体发生了什么动作。

可用动作包括：

- 谁接手客户。
- 谁主持会议。
- 谁签字。
- 谁背责任。
- 谁保留资源。
- 谁协调跨部门。
- 谁承担替换成本。
- 谁在群里同步。
- 谁负责验收。

错误：

```text
信任不能交接。
```

正确：

```text
客户今天愿意接电话，不一定是因为公司，而是因为过去一直是这个人帮他解决问题。
```

## EP-03｜解释一句，推进一句

正文不能连续解释三段。

推荐节奏：

```text
提出现象
↓
解释原因
↓
继续追问
↓
再解释
↓
得到规律
```

每完成一次解释，下一段必须推进问题，而不是换一种说法继续解释。

常用推进句：

- 真正麻烦的是……
- 这还不是最关键的。
- 问题到这里才出现。
- 所以老板真正看的不是……
- 你再往下看，会发现……

## EP-04｜每一段回答一个隐含问题

每段必须回答一个读者心里的小问题。

例如管理题可以按以下隐含问题推进：

- 为什么老板不裁？
- 为什么不能马上换？
- 为什么这些东西不能交接？
- 怎么判断组织已经开始换人？
- 普通人应该看什么信号？

禁止一段只承担情绪渲染或口号总结。

## EP-05｜抽象后立即举组织场景

抽象词后必须立刻落地。

出现以下词时，后面必须接一个具体组织场景：

- 组织信任
- 组织信用
- 责任边界
- 利益分配
- 风险传导
- 授权
- 管理成本
- 规则
- 资源
- 选择权

可落地场景：

- 客户
- 团队
- 项目
- 流程
- 会议
- 汇报
- 绩效
- 晋升
- 交接
- 离职
- 责任

## EP-06｜结尾不是总结，是工具

结尾不能只是复述全文。

结尾必须给读者一个以后能使用的判断工具、观察信号或决策标准。

错误：

```text
所以老板是在算账。
```

正确：

```text
如果你以后发现一个中层开始频繁陪老板见客户、主持跨部门会议、接手关键项目，这往往说明组织已经开始准备交接。
```

结尾必须能让读者完成一句话：

```text
以后我判断这类事，可以看________。
```

## EP-07｜首屏必须给继续阅读理由

正文前 120 字必须完成至少一项：

- 指出一个反常现象。
- 纠正一个常见误解。
- 命中读者真实困惑。
- 给出一个具体后果。
- 承诺一个判断标准。

禁止开头只写正确但平的定义。

## EP-08｜每 3 到 5 段必须出现现实画面

正文不能长时间停留在观点和机制。

每 3 到 5 段必须出现一次：

- 职场动作。
- 组织场景。
- 对话。
- 判断标准。
- 可观察信号。

如果连续 5 段没有现实画面，必须重写。

## EP-09｜少写“是什么”，多写“你会看到什么”

读者更容易被可观察信号带走，而不是被定义带走。

优先表达：

```text
你会看到……
```

少用：

```text
这本质上是……
```

表达顺序优先：

```text
现象
↓
动作
↓
机制
↓
判断
```

不要默认：

```text
概念
↓
定义
↓
解释
↓
举例
```

## EP-10｜不要平均用力，必须有推进峰值

正文不能每段都同等重要。

至少设置一个推进峰值，让读者感觉“这里说透了”。

常见峰值位置：

- 首屏反差后第一次解释。
- 中段揭示利益分配。
- 后段给出判断标准。

峰值句不是金句，而是信息密度更高的判断。

例如：

```text
很多下属不是没有意愿，而是早就发现：主动承担责任以后，收益不一定归自己，风险却一定先落到自己身上。
```

## EP-11｜场景只用高频，不用猎奇

正文场景优先使用普通读者每天见到的组织动作：

- 开会
- 汇报
- 群消息
- 项目推进
- 绩效沟通
- 客户交接
- 晋升提名
- 任务验收
- 离职交接

禁止用低频、戏剧化、无法验证的故事当主案例。

## EP-12｜表达要短句推进，不做讲座

知乎正文适合短段、短句和连续推进。

每段只完成一个动作：

- 提出问题。
- 解释原因。
- 补一个场景。
- 给一个判断。
- 推到下一层。

禁止一段同时完成定义、解释、例子、升华和建议。

## 输出前表达自检

正文输出前必须自检：

- 首屏是否先讲现象或具体困惑。
- 每个机制是否落到具体动作。
- 是否存在连续三段解释但没有推进。
- 每段是否回答一个隐含问题。
- 抽象词后是否接了组织场景。
- 结尾是否给出判断工具，而不是总结。
- 是否每 3 到 5 段出现现实画面。
- 是否出现了至少一个推进峰值。

任一不满足，必须重写正文。

自检只用于生成前判断，不得输出。
