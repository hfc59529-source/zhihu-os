# Consistency Engine V1.0

版本：CONSISTENCY-ENGINE-V1.0

执行版本：ZH-RUNTIME-V3.0-TEACHER

状态：FROZEN（冻结）

---

## 概述

Consistency Engine 不是新增参数，而是**最终验收层**。

它的职责：在所有维度都分别检查通过的情况下，再检查一次"是否所有维度同时达标"。

组成：
1. **硬规则检查**（机械化脚本）
2. **AI 语义审核**（结构化人工或 AI 判断）
3. **固定输出格式**

---

## 第一层：硬规则检查

由 `scripts/validate_consistency_engine.py` 执行。

### 检查项

| 检查项 | 硬规则 | PASS 标准 |
|------|------|---------|
| Primary Goal 唯一性 | 必须 | 且仅有一个 Goal 被勾选 |
| Behavior Goal 字段完整性 | 必须 | 所有 4 个字段都已填写 |
| 目标动作理由 | 必须 | 字符数 > 20 |
| 触发机制 | 必须 | 字符数 > 30 |
| 结果位置 | 必须 | 指明具体某一段 |
| 禁止牺牲项标记 | 必须 | 至少标记 1 项 |
| 基础维度记录 | 必须 | 4 大基础维度都有检查记录 |
| 未处理的 FAIL | 禁止 | 不能有孤立的失败记录 |

**输出**：
- ✓ PASS：所有硬规则检查通过
- ✗ FAIL：列出所有违反的硬规则

## 第二层：AI 语义审核

由 Claude 或人工审核员执行。

### 审核清单（按顺序）

#### 1. 目标机制真实性检查

**问题**：目标触发机制是否真正进入了正文？

**审核方式**：
- 读取 Production Card 中的"触发机制"定义
- 在正文中搜索该机制是否出现
- 检查出现的形式（显性、隐性、部分体现、完全缺失）

**PASS 标准**：
- 触发机制在正文中真实存在
- 出现形式符合该 Goal 的特征
  - 点赞：情绪/立场表达自然流畅
  - 收藏：框架/判断标准明确呈现
  - 评论：留下可讨论的开放点
  - 转发：观点表述精准可引用
  - 关注：认知差异或可信度明显

**FAIL 情况**：
- 触发机制完全缺失
- 虽然有但形式不符 Goal 特征
- 触发机制被其他内容淹没

**输出**：
```
Goal Delivery：PASS / FAIL
Mechanism Found：是/否/部分
Location Match：段落 X 中第 Y 行
Quality Assessment：{具体评价}
```

---

#### 2. 目标价值充分性检查

**问题**：用户是否真的会因此产生目标动作？目标动作理由是否充分？

**审核方式**：
- 读取 Card 中的"用户为什么会做这个动作"
- 检查正文是否真的满足了这个理由
- 判断理由是否充分、是否真实

**PASS 标准**：
- Card 中的理由在正文中有真实支撑
- 理由的强度与 Goal 特征匹配
  - 点赞：共鸣程度足够
  - 收藏：框架可复用性真实
  - 评论：冲突点或开放性真实
  - 转发：观点对用户足够有价值
  - 关注：认知差异足够显著

**FAIL 情况**：
- 理由在正文中无支撑
- 理由虽然在但强度不足
- 理由是假设，不是正文真实内容

**输出**：
```
Goal Sufficiency：PASS / FAIL
Rationale Support：{具体支撑情况}
Strength Level：强/中/弱
```

---

#### 3. 维度冲突检查

**问题**：是否为了达成目标而损害了禁止牺牲的维度？各维度是否互相支持还是互相抵消？

**审核方式**：
- 检查 Card 中"禁止牺牲项"的每一项
- 判断正文中是否真正保持了这些维度
- 检查各维度之间是否有冲突

**PASS 标准**：
- 所有禁止牺牲的维度在正文中都有体现
- 维度之间相互支持，不互相削弱
- 为了 Goal 的优化不是以牺牲其他关键维度为代价

**FAIL 情况**：
- 为了"阅读顺畅"砍掉了"推理完整"
- 为了"认知深度"牺牲了"可信度"
- 为了"观点鲜明"放弃了"问题回应"

**FAIL 例子**：

```
禁止牺牲项：阅读顺畅、可信度
检查结果：
  - 阅读顺畅：正文有被动语态堆砌，第 3 段特别难读 ✗
  - 可信度：有 2 处无来源数字 ✗
整体判定：FAIL
原因：为了框架完整性（收藏 Goal），削弱了阅读体验
```

**输出**：
```
Dimension Conflict：PASS / FAIL
Sacrificed Items：{列表}
Support Level：强支持/支持/平衡/冲突/对立
```

---

#### 4. 具体失败段落定位

**问题**：如果有失败，具体是哪一段出现问题？是内容问题还是表达问题？

**审核方式**：
- 逐段检查，定位问题所在
- 判断问题类型（内容缺失、表达不当、结构混乱、逻辑破裂）
- 给出具体改进方向

**输出格式**：

```
Failed Segments：段落 3、段落 5

段落 3 问题：
  类型：内容缺失
  描述：缺少该 Goal 必需的具体案例
  改进：补充 1 个真实场景

段落 5 问题：
  类型：表达不当
  描述：观点过于绝对，违反"保留余地"原则
  改进：改为"在多数情况下"而非"必然"
```

---

#### 5. 修正建议

**问题**：如需修正，是 Claude 二稿，还是回退 Production Card？

**决策标准**：

| 失败类型 | 数量 | 建议 |
|---------|------|------|
| 硬规则失败 | 任何 | 回退 Card（硬规则必须前置冻结） |
| 目标机制缺失 | - | 回退 Card（需要重新规划结构） |
| 目标充分性不足 | - | 回退 Card 或二稿（取决于是否能填补） |
| 维度冲突 | 1-2 项 | 二稿修正 |
| 维度冲突 | 3+ 项 | 回退 Card（冲突太多） |
| 段落问题 | < 2 段 | 二稿修正 |
| 段落问题 | ≥ 2 段 | 回退 Card 或二稿评估 |

**输出**：

```
Final Decision：

若 PASS：
  Recommendation：发布

若 FAIL 且可修正：
  Recommendation：Claude 二稿
  Fix Strategy：{具体修改指导}

若 FAIL 且需重做：
  Recommendation：回退 Production Card
  Reason：{根本原因}
  Guidance：{重做建议}
```

## 调用规则

### 什么时候触发 Consistency Engine

1. Production Card 通过 `validate_production_card.py`
2. 正文通过 `validate_reasoning.py`
3. Skill007 QA 审核（初版）

**顺序**：
```
PC 校验 PASS
  ↓
Claude 生成
  ↓
推理校验 PASS
  ↓
QA 审核 PASS（初版）
  ↓
Consistency Engine（最终层）
  ├─ 硬规则 PASS
  ├─ AI 语义审核 PASS
  └─ 输出最终验收报告
    ├─ PASS → 发布
    ├─ FAIL（可修正） → Claude 二稿 → 重新审核
    └─ FAIL（需回退） → 退回 Production Card
```

### 谁来执行

- **硬规则检查**：自动脚本（`validate_consistency_engine.py`）
- **AI 语义审核**：Claude 或人工审核员
- **最终决策**：人工确认
