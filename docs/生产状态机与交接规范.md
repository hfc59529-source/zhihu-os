# 生产状态机与交接规范

状态：ACTIVE
日期：2026-08-09

本文件是 `docs/知乎OS Compiler V1.md` 七节点（INPUT/DECISION/COMPILE/WRITE/AUDIT/REVIEW/RELEASE）在状态机层面的唯一权威载体，同时是 `Runtime.Release Rules` 的唯一权威（即 RELEASE 节点"USER_APPROVED 才能进入 RELEASE"这条规则唯一定义在本文件）。`data/Publish_Queue.md` 只消费本文件定义的 `RELEASE_READY` 状态，不重复维护 Release Gate 规则本身。

本文件的状态命名空间是 Production 生命周期状态（`TOPIC_PACKAGE_READY` … `RELEASE_READY` … `PUBLISHED`），与 Compiler V1 RELEASE 节点内部的 `READY_FOR_RELEASE → RELEASED` 状态转换不是同一命名空间，两者不需要同名同构：`RELEASE_READY` = Production 已具备进入发布队列资格，`RELEASED` = Compiler RELEASE 节点内部状态转换完成的记录。

## 核心规则

任何角色完成本阶段后，只能更新状态并交接给下一责任角色，不能替下一角色继续决策。

状态只有在该阶段的必要输出和校验证据全部存在时，才能向下流转。

### Triggered Rule IDs compatibility rule（2026-08-11，TRIAL Runtime）

当且仅当当前 Runtime Release 尚未发布任何 ID-bearing conditional Runtime.Audit Rules 固定候选集合，且 COMPILE 已完成 Reasoning Path / Structure / Material Boundary / Expression Constraints / Acceptance Criteria 五项输出时，Execution IR 可在 Triggered Rule IDs 字段记录 `[]`；该空集合视为 Triggered Rule IDs 字段已如实完成，可满足 `EXECUTION_IR_READY` 的完整性判定。

Global Operational Checks 继续由 Runtime 的 AUDIT 执行载体直接加载，不依赖 Triggered Rule IDs。本兼容规则只恢复 COMPILE → WRITE continuity，不创建新的 Production Status，不构成 Human Override / Waiver 通用机制，不改变 AUDIT / REVIEW / RELEASE Gate，不决定 Compiler §14 Production Validation 计数资格。

## Codex 采集与维护边界

Codex 在单篇生产前只负责选题采集与入库，到形成可供生产的选题包为止。Production Card、正文、QA、审核、修正和发布均由 Claude、GPT / 人工或用户接管。

Codex 在系统层负责维护参数库、知识库、样本库和参数调用日志。系统维护只能在 GPT / 人工确认系统问题后执行，不能混入单篇正文生产。

Codex 禁止生成 Production Card、提炼核心观点、设计文章结构、安排段落、生成正文或修正文案。

## Codex 正文禁写边界

Codex 禁止直接创建、改写、润色或替换以下正文类文件的正文内容：

- `Draft-v1.md`
- `Article-v*.md`
- `Article-Patched-v*.md`
- `Article-Final.md`
- `Release-v*.md` 中的正文段落

Codex 不进入正文审核与 Patch。若后续生产角色发现正文问题，由 Claude / 写作角色执行正文修正。

Codex 允许编辑的文件范围：

- `data/Topic_Pool.md`
- `data/topic_candidates/YYYY-MM-DD/TOPIC-YYYYMMDD-NNN.md`
- `data/parameter_call_log.md`
- 参数库、知识库、样本库中经确认需要维护的记录

`Release-v*.md` 不属于 Codex 当前单篇职责。

## 修改后确认与发布入口

Audit PASS / Issue = 0 后直接进入 `READY_FOR_USER_REVIEW`，不空跑 Decision，不执行修改后确认。

只有发生 Patch 后，才进入 `PATCH_VALIDATED`，由 GPT / 人工确认修改有效；通过后进入 `READY_FOR_USER_REVIEW`。

只有用户明确 `USER_APPROVED` 后，后续生产角色才能生成或确认 `Release-v1.md`，并将状态更新为 `RELEASE_READY`。

`RELEASE_READY` 是进入 `data/Publish_Queue.md` 的唯一生产状态入口；已存在 `Release-v1.md` 不能单独作为入队依据。

## 用户验收包

进入 `READY_FOR_USER_REVIEW` 时，必须生成或展示用户验收包。验收包不是正文修订文件，不得改写正文，只负责把用户验收所需上下文放在同一处。

用户验收包必须包含：

- Production ID。
- 原知乎问题。
- 真实知乎问题链接。
- 当前正文版本和来源文件，例如 `Draft-v1.md` 或 `Article-Patched-v1.md`。
- 当前状态，例如 `READY_FOR_USER_REVIEW`。
- 完整正文内容。

正文文件（`Draft-v1.md` / `Article-Patched-v1.md`）可以保持纯正文，便于复制到知乎；但交给用户验收时，不得只展示无头正文。

未获得 `USER_APPROVED` 前，不得把 `Release-v1.md` 当作用户验收包或正式发布稿使用。若历史流程已经生成 `Release-v1.md`，只能作为历史参考，不得作为当前入队依据。

## REVIEW DIAGNOSIS：成稿诊断语言

本节用于正文完成后的质量诊断与 Revision 定位。

它不是正文生成配方，不构成 WRITE 阶段的强制要求，也不要求每篇文章同时具备全部维度。

禁止因为某一维度"不足"，机械补写对应内容。

例如：

- 人性不足 ≠ 强行增加一段人性分析
- 机制不足 ≠ 强行增加抽象机制解释
- 反转不足 ≠ 必须制造反转
- 价值不足 ≠ 结尾强塞建议
- 冲突不足 ≠ 人为激化矛盾

10 维的唯一作用是：

> 判断成稿当前最大的质量瓶颈在哪里，并确定最小修改方向。

### 十个诊断维度

#### 1. 对题

检查正文是否真正回答了题目，而不是借题发挥。

核心问题：

> 如果删掉题目，这篇文章是否仍然可以原封不动回答另一个问题？

若可以，说明存在跑题或泛化风险。

#### 2. 受众命中

检查正文是否回答了"真正会点开这个问题的人"想知道的东西。

对题解决的是：

> 我有没有回答这个问题？

受众命中解决的是：

> 读者点进来真正想得到的答案，我有没有给？

需要区分：

- 提问者表面在问什么
- 提问者真正困惑什么
- 围观读者为什么会点进来
- 他们希望获得解释、判断、预测还是行动依据

#### 3. 冲突

检查文章是否抓住了真实存在的矛盾，而不是只有正确解释。

冲突可以来自：

- 利益冲突
- 权力冲突
- 角色冲突
- 规则冲突
- 认知与现实冲突
- 短期与长期利益冲突

核心问题：

> 到底是哪两个东西不能同时成立？

没有冲突，文章容易正确但平。

#### 4. 人性

检查是否解释了行为主体"为什么会这么做"。

重点不是道德评价，而是识别：

- 欲望
- 恐惧
- 自利
- 风险规避
- 身份需求
- 控制欲
- 损失厌恶
- 利益计算
- 自我合理化

人性分析必须服务于当前问题，不要求每篇显性出现。

#### 5. 机制

检查正文是否从现象继续推到了背后的运行逻辑。

核心问题：

> 这件事为什么会稳定地发生，而不只是这一次碰巧发生？

机制应解释因果关系，而不是给现象重新命名。

避免为了显得有深度而制造抽象概念。

#### 6. 递进

检查后一段是否真正推进了前一段。

有效递进至少应完成一种变化：

- 新增信息
- 加深因果
- 改变视角
- 扩大解释范围
- 推出预测
- 推出判断标准
- 推向行动

核心判断：

> 后一段有没有给读者新的东西？

如果只是换一种高级说法重复上一段，即使每句话都正确，也属于递进失败。

#### 7. 反转

检查文章是否存在对读者原有认知模型的有效修正。

反转不是强制项。

真正有效的反转应来自推理，例如：

> 你以为问题是 A，真正决定结果的是 B。

禁止为了制造爽感而人为反转、故意唱反调或制造伪洞察。

没有真实反转时，可以没有反转。

#### 8. 价值 / 落地

检查读者看完以后，是否获得了新的判断能力、预测能力或行动依据。

价值不等于"给建议"。

更高质量的落地通常是：

> 给读者一个以后可以重复使用的判断变量。

例如：

- 看什么信号
- 区分什么情况
- 哪个变量发生变化意味着性质改变
- 下一次遇到类似问题应该先判断什么

正文不要求必须出现操作步骤。

#### 9. 表达效率

检查单位篇幅内的信息推进效率。

重点识别：

- 同义重复
- 已经证明后继续证明
- 一个观点换多个概念重复包装
- 解释超过理解所需
- 金句重复表达同一结论
- 作者展示认知多于服务读者

核心问题：

> 这句话删掉以后，读者会不会损失新的信息？

如果不会，优先考虑删除。

#### 10. 阅读张力

检查文章是否持续给读者"继续往下读"的理由。

阅读张力可以来自：

- 未解决的问题
- 冲突升级
- 信息差
- 反常识
- 新变量出现
- 预测
- 场景推进
- 认知反转

注意：

> 逻辑正确 ≠ 有阅读张力。

如果文章连续多段只解释同一个结论，即使机制正确，也会产生阅读疲劳。

### 使用规则

10 维诊断不得采用"缺什么补什么"的 Revision 逻辑。

正确流程：

```text
成稿 → 10维诊断 → 找主要瓶颈 → 最小修改 → 重读
```

每轮优先定位 1-2 个主要瓶颈。

禁止为了提高所有维度评分而全面重写正文。

若正文核心逻辑、冲突和结构已经成立，应优先采用：

- 删除
- 压缩
- 调序
- 替换
- 局部补强

而不是重新生成全文。

### 诊断输出原则

诊断时不追求"十项高分"。

目标是识别：

> 当前最影响这篇文章成立或被读完的变量是什么？

例如：

```text
对题：9
受众命中：9
冲突：9
人性：8.5
机制：9
递进：7
反转：8
价值/落地：9
表达效率：6.5
阅读张力：6.5
```

此时 Revision 结论不应是：

```text
继续补人性、机制、反转和价值。
```

而应该是：

> 主要瓶颈为表达效率与阅读张力。核心内容已经足够，停止增加观点，删除重复解释并恢复阅读推进。

### 总原则

> 10维是体检表，不是配方表。

它不决定文章应该写什么。

它只负责判断：

```text
文章已经写出来以后，问题到底出在哪里。
```

最终 Revision 原则：

> 诊断，不补零件。
>
> 找到瓶颈，只修瓶颈。
>
> 能删不加，能局部修不重写。
